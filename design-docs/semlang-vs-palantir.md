# SemLang vs Palantir Ontology

This comparison focuses on ontology-system functionality: modeling, querying, operational writeback, governance, developer access, and application/runtime surfaces.
SemLang status is based on the local V1 language and action documentation; Palantir status is based on public Palantir Foundry documentation reviewed in May 2026.

Legend: `✓` = supported, `△` = partial or planned, `X` = not supported or not documented as a comparable capability.

## Functionality Comparison

| Functionality                                      | SemLang | Palantir | Comments                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------- | ------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ontology resources as a managed artifact           | △       | ✓        | SemLang models packages, concepts, types, lenses, queries, and actions in source files. Palantir Ontologies are managed platform artifacts containing object types, link types, action types, interfaces, shared properties, and object type groups. See Palantir [Ontologies overview](https://www.palantir.com/docs/foundry/ontologies/ontologies-overview).                                                                                                             |
| Object/concept types backed by data                | ✓       | ✓        | SemLang `concept ... from ...` maps a semantic concept to a Malloy-compatible source. Palantir object types map ontological concepts to backing data sources. See Palantir [object type docs](https://www.palantir.com/docs/foundry/object-link-types/create-object-type).                                                                                                                                                                                                 |
| Properties / source-backed fields                  | ✓       | ✓        | SemLang `field:` blocks attach semantic types to source columns. Palantir properties define object characteristics and property values. See Palantir [Properties overview](https://www.palantir.com/docs/foundry/object-link-types/properties-overview/).                                                                                                                                                                                                                  |
| Primary keys / identity                            | ✓       | ✓        | SemLang `identity` lowers to Malloy `primary_key`; Palantir object instances have primary keys and property values.                                                                                                                                                                                                                                                                                                                                                        |
| Semantic value types with constraints              | ✓       | ✓        | SemLang `type:` supports primitive semantic domains plus JSON Schema-style metadata. Palantir value types are reusable semantic wrappers with validation constraints and versions. See Palantir [Value types](https://www.palantir.com/docs/foundry/object-link-types/value-types-overview/) and [Value type constraints](https://www.palantir.com/docs/foundry/object-link-types/value-type-constraints/).                                                                |
| Shared property definitions                        | X       | ✓        | SemLang can reuse semantic value types, but field/property declarations are local to concepts. Palantir supports shared properties for centralized property metadata across object types. See Palantir [Shared properties](https://www.palantir.com/docs/foundry/object-link-types/shared-property-overview).                                                                                                                                                              |
| Struct / nested property types                     | X       | ✓        | SemLang currently supports scalar primitives and does not model records, arrays, or structs. Palantir supports struct property types, with some platform-availability caveats. See Palantir [Structs overview](https://www.palantir.com/docs/foundry/object-link-types/structs-overview/).                                                                                                                                                                                 |
| Link types / relationships                         | ✓       | ✓        | SemLang uses `join_one`, `join_many`, and `join_cross` as semantic relationships that lower to Malloy joins. Palantir link types define relationships between object types and can be traversed by applications and APIs. See Palantir [Link types](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview).                                                                                                                                          |
| Many-to-many relationship modeling                 | ✓       | ✓        | SemLang can model many-side joins and relationship objects as `relator` concepts. Palantir supports many-to-many link types, including link datasources.                                                                                                                                                                                                                                                                                                                   |
| gUFO / OntoUML-style classifiers                   | ✓       | X        | SemLang has explicit `kind`, `event`, `situation`, `relator`, and `phase of Parent` stereotypes. Palantir public docs describe generic object types, interfaces, and groups rather than these ontological classifier categories.                                                                                                                                                                                                                                           |
| Roles as named predicates                          | ✓       | X        | SemLang supports `role Name when predicate` and role tests in expressions. Palantir has permissions roles and object type groups, but public docs do not show an equivalent named-predicate role construct for object classification.                                                                                                                                                                                                                                      |
| Interfaces / polymorphic object shapes             | X       | ✓        | SemLang has phase and role semantics but no interface/polymorphism construct. Palantir interfaces define abstract shapes and capabilities implemented by multiple object types. See Palantir [Interfaces overview](https://www.palantir.com/docs/foundry/interfaces/interface-overview/).                                                                                                                                                                                  |
| Temporal axes and valid-time joins                 | ✓       | X        | SemLang has `occurrence_time`, `valid_time`, `observation_time`, `recorded_time`, and `at` temporal join lowering. Palantir can model time properties and has event/time-series applications, but public Ontology docs do not describe first-class valid-time axes or temporal join semantics.                                                                                                                                                                             |
| Derived fields / metrics                           | ✓       | ✓        | SemLang supports `dimension:` and `measure:` declarations that lower to Malloy. Palantir supports derived properties and object-set aggregations. See Palantir [Derived properties](https://www.palantir.com/docs/foundry/object-link-types/derived-properties/) and [Object sets API](https://www.palantir.com/docs/foundry/functions/api-object-sets).                                                                                                                   |
| Named views and analytical queries                 | ✓       | △        | SemLang supports Malloy-shaped views and named queries. Palantir supports object-set search/filter/order/aggregate APIs and beta Ontology SQL in Object Explorer, but this is not a Malloy-style semantic query language. See Palantir [Search Objects API](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/ontology-objects/search-objects/) and [Analyze objects using SQL](https://www.palantir.com/docs/foundry/object-explorer/analyze-sql).        |
| Query-time semantic overlays                       | ✓       | X        | SemLang lenses can refine concepts at query time and compose left-to-right. Palantir supports branches, applications, object views, and filters, but public docs do not describe a direct query-local semantic overlay equivalent.                                                                                                                                                                                                                                         |
| Validation predicates / data-quality rules         | △       | △        | SemLang parses and preserves `validation:` predicates but does not emit analytical validation execution by default. Palantir has value-type constraints, required properties, submission criteria, and validation-like app/workflow features, but not a direct named invariant false-row construct in the core ontology docs.                                                                                                                                              |
| Object search and exploration UI                   | X       | ✓        | SemLang has MCP semantic search over model metadata, but no end-user object search UI. Palantir Object Explorer searches, filters, analyzes, compares, visualizes, exports, and applies Actions to object sets. See Palantir [Object Explorer](https://www.palantir.com/docs/foundry/object-explorer/overview).                                                                                                                                                            |
| Semantic/vector search over objects                | X       | ✓        | SemLang MCP `search` is metadata/name/expression search, not embedding-backed object retrieval. Palantir documents semantic search workflows with embeddings associated to Ontology objects. See Palantir [Semantic search](https://www.palantir.com/docs/foundry/ontology/overview-semantic-search).                                                                                                                                                                      |
| Agent / reasoning tools over the ontology          | ✓       | ✓        | SemLang exposes MCP tools for semantic search, concept/action descriptions, path finding, lens planning, query validation/running, and local action invocation. Palantir exposes Ontology/AIP capabilities through AIP Analyst, Agent Studio tools, OSDK, and platform APIs. See Palantir [AIP Analyst](https://www.palantir.com/docs/foundry/aip-analyst/overview).                                                                                                       |
| Action types / controlled object edits             | △       | ✓        | SemLang action declarations model subjects, params, guards, edits, logs, effects, and agent metadata; current docs frame runtime adapters/action manifests as the boundary. Palantir Actions are platform-native transactions that change objects, properties, and links. See Palantir [Action types](https://www.palantir.com/docs/foundry/action-types/overview).                                                                                                        |
| Action parameters and submission criteria          | ✓       | ✓        | SemLang actions support semantic typed params and guards. Palantir action types support parameters and submission criteria. See Palantir [Action parameters](https://www.palantir.com/docs/foundry/action-types/parameter-overview/) and [Submission criteria](https://www.palantir.com/docs/foundry/action-types/submission-criteria/).                                                                                                                                   |
| Function-backed actions / arbitrary business logic | X       | ✓        | SemLang does not have a function repository or function-backed action runtime. Palantir functions can read object/link data and modify objects through function-backed Actions. See Palantir [Functions on objects](https://www.palantir.com/docs/foundry/functions/functions-on-objects) and [Function-backed actions](https://www.palantir.com/docs/foundry/action-types/function-actions-overview).                                                                     |
| Writeback runtime and transactions                 | △       | ✓        | SemLang can describe write plans and locally invoke supported actions against DuckDB example data, but it lacks a durable platform writeback service. Palantir Actions and Functions support Ontology edits, materializations, and beta transaction functions. See Palantir [Object edits](https://www.palantir.com/docs/foundry/object-edits/overview/) and [Ontology transactions](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-transactions). |
| Side effects / notifications / webhooks            | △       | ✓        | SemLang can declare `effect` blocks for runtime adapters, but no built-in effect delivery exists. Palantir Action side effects include notifications and webhooks. See Palantir [Action side effects](https://www.palantir.com/docs/foundry/action-types/side-effects-overview/).                                                                                                                                                                                          |
| Action logs, edit history, and undo                | △       | ✓        | SemLang can describe action log metadata, but has no persistent object-level edit history or revert service. Palantir supports action logs, edit history, and OSv2 action reverts. See Palantir [Action log](https://www.palantir.com/docs/foundry/action-types/action-log), [Edit History widget](https://www.palantir.com/docs/foundry/workshop/widgets-edits-history/), and [undo actions](https://www.palantir.com/docs/foundry/action-types/action-reverts/).         |
| Granular object/property/link security             | X       | ✓        | SemLang has no authorization model beyond whatever a downstream runtime enforces. Palantir documents resource-level and object/link data permissions, including object and property policies. See Palantir [Object permissioning](https://www.palantir.com/docs/foundry/object-permissioning/overview) and [Managing object security](https://www.palantir.com/docs/foundry/object-permissioning/managing-object-security/).                                               |
| Resource permissions and branch protection         | X       | ✓        | SemLang source files can be governed by repository permissions, but the language has no ontology-resource permission model. Palantir ontology resources can use project permissions and branch protection. See Palantir [Ontology permissions](https://www.palantir.com/docs/foundry/ontologies/ontology-permissions/) and [Branching the ontology](https://www.palantir.com/docs/foundry/ontologies/branching-ontology).                                                  |
| Branching, proposals, review, and merge            | X       | ✓        | SemLang has ordinary file/git workflows only. Palantir integrates ontology changes with Global Branching, ontology proposals, reviewers, merge checks, rebasing, and conflict resolution. See Palantir [Branching the ontology](https://www.palantir.com/docs/foundry/ontologies/branching-ontology).                                                                                                                                                                      |
| Export/import ontology definitions                 | ✓       | △        | SemLang is already text-first. Palantir supports exporting/importing Ontology JSON, but warns not to depend on the exported schema remaining stable. See Palantir [Export, edit, and import an Ontology](https://www.palantir.com/docs/foundry/ontology-manager/export-import/).                                                                                                                                                                                           |
| Generated SDKs and APIs                            | △       | ✓        | SemLang has CLI and MCP surfaces, but no generated TypeScript/Python/Java/OpenAPI SDK. Palantir OSDK supports TypeScript, Python, Java, and OpenAPI, with high-scale queries and writeback. See Palantir [OSDK overview](https://www.palantir.com/docs/foundry/ontology-sdk/overview).                                                                                                                                                                                     |
| Object storage / indexing backend                  | X       | ✓        | SemLang compiles to Malloy and can run queries through configured Malloy connections, but does not provide an ontology object store. Palantir Object Storage indexes, stores, queries, and manipulates Ontology objects. See Palantir [Ontology architecture](https://www.palantir.com/docs/foundry/object-backend/overview).                                                                                                                                              |
| Materializations for latest object state           | X       | ✓        | SemLang does not maintain edited object state. Palantir materializations combine source data and user edits into downstream datasets. See Palantir [Materializations](https://www.palantir.com/docs/foundry/object-edits/materializations/).                                                                                                                                                                                                                               |
| Lineage, usage, and observability                  | X       | ✓        | SemLang has compiler diagnostics and requirement traceability, not runtime lineage or usage metrics. Palantir exposes Ontology usage metrics and broader workflow/data lineage. See Palantir [Ontology Manager usage](https://www.palantir.com/docs/foundry/ontology-manager/view-usage/) and [Workflow Lineage](https://www.palantir.com/docs/foundry/workflow-lineage/overview).                                                                                         |
| Low/no-code application surfaces                   | X       | ✓        | SemLang is a language/tooling layer. Palantir connects Ontology data to Object Explorer, Object Views, Workshop, Vertex, Map, Foundry Rules, and other operational applications. See Palantir [Ontology-aware applications](https://www.palantir.com/docs/foundry/ontology/applications) and [Object Explorer](https://www.palantir.com/docs/foundry/object-explorer/overview).                                                                                            |
| Marketplace packaging / reuse                      | X       | ✓        | SemLang has includes and repo reuse, but no platform marketplace. Palantir can package object/link/interface/action types in Marketplace products, subject to documented limits. See Palantir [Marketplace ontology types](https://www.palantir.com/docs/foundry/object-link-types/marketplace-ontology-types).                                                                                                                                                            |
| RDF / OWL / SPARQL-native semantics                | X       | △        | SemLang is inspired by gUFO/OntoUML and lowers to Malloy, not RDF/OWL/SPARQL. Palantir docs say data types are inspired by RDF, OWL, and XSD, but the public Ontology surface is an operational object/action system rather than a standards-native reasoner or SPARQL endpoint. See Palantir [Types reference](https://www.palantir.com/docs/foundry/object-link-types/type-reference).                                                                                   |

## High-Level Gap Summary

SemLang is strongest as a compact, text-first semantic modeling and analytical query layer.
It has richer explicit ontological classifiers than Palantir's public Ontology model and a clean Malloy lowering story for read analytics.

Palantir is strongest as an operational ontology platform.
The biggest gaps for SemLang relative to Palantir are durable object storage/indexing, governed writeback, function-backed actions, object-level security, end-user applications, generated SDKs, branching/proposal workflows, materializations, lineage, observability, and semantic/vector search over object data.
